  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.1 SCORE DIVIDIDO POR 100 🔴 CRÍTICO                             │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    El Score de Calidad mostraba valores entre 0.1% y 10% en vez de
    10% a 100%. Todas las evaluaciones aparecían como "Críticas"
    (score < 90%) aunque no lo fueran.

  DIAGNÓSTICO:
    En la hoja "Evalucion", fila 17, la fórmula del score por factor
    tenía un `/100` extra:

    ❌ = +F17*1/G17/100

    Ejemplo con 3 respuestas correctas de 4 preguntas:
    → 3 × 1 / 4 / 100 = 0.0075 (0.75%) ← MAL

    ✅ Debería ser:
    = +F17*1/G17
    → 3 × 1 / 4 = 0.75 (75%) ← BIEN

  IMPACTO:
    - Todos los scores de factores individuales estaban 100× más pequeños
    - Tablas dinámicas promediaban valores incorrectos
    - Gráficos del PPT semanal mostraban datos erróneos
    - Clasificación "Crítica/No Crítica" incorrecta
    - Ranking de agentes distorsionado

  SOLUCIÓN:
    Multiplicar todos los scores por 100 al extraer los datos del .xlsm:
    Python: if score < 1: score = score * 100

    Ver archivo: Ingris/dashboard/scripts/extract_data.py
    Línea: `score = score * 100` (se aplica a TODOS los valores < 1)


  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.2 SCORE LEÍA COLUMNA EQUIVOCADA 🔴 CRÍTICO                      │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    El score extraído no coincidía con el Score de Calidad total.
    Valores inconsistentes entre evaluaciones.

  DIAGNÓSTICO:
    El script de extracción buscaba la palabra "SCORE" y encontraba
    primero la columna "Apertura y cierre corporativo Score" (Col 114)
    en vez de "SCORE CALIDAD" (Col 187).

    Col 114 = Score de un factor individual (ej: 0.15 = 15%)
    Col 187 = Score de Calidad TOTAL (ej: 0.75 = 75%) ← LA CORRECTA

  SOLUCIÓN:
    Priorizar la búsqueda: primero buscar "SCORE CALIDAD" exacto,
    luego "SCORE" genérico como fallback.

    Python:
    ```python
    score_col = col_idx.get('SCORE CALIDAD')
    if score_col is None:
        score_col = col_idx.get('Score calidad')
    if score_col is None:
        # Fallback: buscar cualquier columna con SCORE
        ...
    ```

  IMPACTO:
    Los scores individuales de factores se usaban como score total,
    dando valores muy por debajo del score real (ej: 15% vs 75%).


  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.3 DUPLICACIÓN AL EXTRAER DATOS 🟡                               │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    El dashboard mostraba el doble de evaluaciones de las esperadas
    (900 en vez de 450).

  DIAGNÓSTICO:
    El script ejecutaba INSERT sin limpiar la tabla primero.
    Cada ejecución duplicaba los registros existentes.

  SOLUCIÓN:
    Agregar DELETE FROM antes del INSERT en el script de extracción:
    ```python
    c.execute('DELETE FROM evaluaciones')
    ```
    Y también limpiar tablas dimensionales para evitar duplicados:
    ```python
    for table in ['evaluaciones', 'agentes', 'supervisores', ...]:
        c.execute(f'DELETE FROM {table}')
    ```


  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.4 REFERENCIAS #REF! ROTAS 🟡                                    │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    Más de 10 fórmulas en la hoja BD mostraban `#REF!` (error de
    referencia). Las preguntas afectadas NO se evaluaban.

  DIAGNÓSTICO:
    Se eliminaron columnas de la hoja BD después de crear las fórmulas.
    Las referencias a esas columnas ahora apuntan a celdas inexistentes.

    Ejemplo de fórmulas rotas:
    ❌ = IF(#REF!="No", #REF!, "")

    Columnas probablemente borradas:
    - Cerca de AQ, AR (preguntas 29-31)
    - Cerca de HT (posiblemente "venta cruzada")
    - Cerca de HU (posiblemente "indagar necesidades")

  SOLUCIÓN EN EL DASHBOARD:
    Las filas con #REF! se omiten automáticamente al extraer los datos
    (el script ignora valores no numéricos). Para arreglar el Excel
    original, habría que restaurar las columnas borradas y actualizar
    las fórmulas.

  │      Evalucion vs Evalucion(2)                                     │

  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.6 FÓRMULA REDUNDANTE /100% 🟢                                   │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    En hoja BD, una fórmula dividía entre 100%, que es matemáticamente
    redundante.

  DIAGNÓSTICO:
    ❌ = IF(SUM(DK4,DP4,DU4,DW4)>335%, 100%, SUM(DK4,DP4,DU4,DW4)/100%)

    100% = 1 en Excel, por lo tanto dividir por 100% es dividir por 1,
    que no hace nada. La intención probable era promediar:

    ✅ = IF(SUM(DK4,DP4,DU4,DW4)>335%, 100%, SUM(DK4,DP4,DU4,DW4)/4)

  SOLUCIÓN:
    No crítica (no afecta el resultado final), pero es código confuso.
    Se documentó en Ingris/formulas.txt para referencia futura.


  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.7 DOBLE CORRECCIÓN PYTHON vs PHP 🟡                             │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    El script Python corregía scores con un umbral (< 0.2 → ×100),
    mientras que el PHP original corregía con otro umbral (< 1 → ×100).

  DIAGNÓSTICO:
    Python: if 0 < score < 0.2: score = score * 100
    PHP:    CASE WHEN AVG(x) < 1 THEN 100 ELSE 1 END

    Esto creaba inconsistencias:
    - Score = 0.10 → Python ×100 = 10.0 → PHP no corrige (10>1) → 10%
    - Score = 0.30 → Python no corrige (0.3>0.2) → PHP ×100 → 30%
    - Score = 0.003 → Python ×100 = 0.3 → PHP ×100 → 30%

    Mismos datos originales, distintas correcciones, resultados dispares.

  SOLUCIÓN:
    Unificar la corrección: Python multiplica TODOS los scores < 1 por 100.
    ```python
    if score < 1:
        score = score * 100
    ```
    Y el PHP ahora no necesita hacer ninguna corrección adicional porque
    los datos ya vienen en porcentaje (0-100).


  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.8 XLOOKUP INEFICIENTE 🟢                                        │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    Fórmula XLOOKUP que escanea toda la columna A:A en vez de un rango.

  DIAGNÓSTICO:
    ❌ = XLOOKUP(A:A, HC!B:B, HC!E:E, , 0)
    Escanea 1,048,576 filas por cada evaluación (450 veces).

    ✅ = XLOOKUP(A2:A450, HC!B2:B100, HC!E2:E100, , 0)
    Escanea solo las filas con datos.

  SOLUCIÓN:
    No crítica pero ralentiza el Excel. Recomendable acotar rangos.


  ┌─────────────────────────────────────────────────────────────────────┐
  │  1.9 SIN BACKEND PARA GITHUB PAGES 🟢                              │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    El dashboard original usaba PHP (api.php + config.php) para servir
    datos desde SQLite. GitHub Pages NO SOPORTA PHP.

  DIAGNÓSTICO:
    La versión PHP requería un servidor con PHP habilitado (XAMPP/LAMP).
    Para GitHub Pages se necesita HTML+JS+CSS estático.

  SOLUCIÓN:
    Se reescribió el dashboard como HTML+CSS+JS puro con los datos
    precargados desde un archivo JSON (data/calidad_data.json).
    Se creó export_json.py para convertir la SQLite → JSON.

    Flujo de trabajo:
    1. python scripts/export_json.py  → genera calidad_data.json
    2. git add Ingris/dashboard/data/calidad_data.json
    3. git push
    4. Abrir en GitHub Pages

  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    Existen 3 bases SQLite con la MISMA estructura pero datos diferentes:
    - iphone_julio_7_24.db (56 KB)
    - sharep.db (~150 KB)
    - promo_3dias.db

  DIAGNÓSTICO:
    Cada DB se creó para un propósito diferente pero con el mismo esquema:
    - iphone_julio_7_24.db → iPhone julio 2026
    - sharep.db → Todos los datos normalizados
    - promo_3dias.db → Solo promoción 3 días

    Esto duplica código y hace difícil mantener la consistencia.
    Si se actualiza una tabla en una DB, hay que actualizar las otras 2.

  SOLUCIÓN RECOMENDADA:
    Unificar en UNA SOLA base de datos con un campo `tipo_extraccion`
    o usar vistas para los diferentes filtros. Ejemplo:

    ```sql
    CREATE VIEW iphone_julio AS
    SELECT * FROM ventas
    WHERE modelo LIKE '%IPHONE%'
      AND strftime('%Y-%m', fecha_creacion) = '2026-07';

    CREATE VIEW promo_3dias AS
    SELECT * FROM ventas
    WHERE promo = 'SI'
      AND dia_crea IN ('Lunes','Miércoles','Viernes');
    ```

  ┌─────────────────────────────────────────────────────────────────────┐
  │  3.2 CUATRO FUENTES DE DATOS NO NORMALIZADAS 🟡                   │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    Los datos están repartidos en 4 archivos Excel diferentes, cada uno
    con estructura distinta. No hay una fuente única de verdad.

  FUENTES:
    Base 1: Nextphone 14072026 (24 cols)
      - Datos: clientes fijo+móvil, canal, supervisor
      - Llave: CUENTA / CUST_NO

    Base 2: Móvil sin fijo 02072026 (23 cols)
      - Datos: clientes solo móvil
      - Llave: CUENTA / CUST_NO

    Base 3: Cross-sell movil (26-28 cols)
      - Datos: segmentación para venta cruzada
      - Llave: CUENTA / CUST_NO

    Base 4: Winback SOHO (10 cols)
      - Datos: clientes perdidos para recuperar
      - Llave: CLIENTE (nombre)

  DIAGNÓSTICO:
    - Sin esquema unificado, cada base tiene columnas diferentes
    - La Base 4 usa nombre de cliente como llave (no CUENTA)
    - Las ejecutivas deben saber qué base usar para cada cliente
    - No hay integridad referencial

  SOLUCIÓN RECOMENDADA:
    Unificar en un modelo de datos SQLite:

    ```sql
    CREATE TABLE clientes (
        cust_no    INT PRIMARY KEY,
        cuenta     INT,
        nombre     TEXT,
        tipo       TEXT,  -- M=Persona, J=Empresa
        provincia  TEXT,
        direccion  TEXT
    );

    CREATE TABLE servicios (
        cust_no     INT,
        servicio    TEXT,  -- Fijo, Movil, Internet
        plan        TEXT,
        monto       DECIMAL,
        descuento   DECIMAL,
        FOREIGN KEY (cust_no) REFERENCES clientes(cust_no)
    );
    ```

  ┌─────────────────────────────────────────────────────────────────────┐
  │  3.4 FORMATO .XLSB INCOMPATIBLE 🟢                                 │
  └─────────────────────────────────────────────────────────────────────┘

  SÍNTOMA:
    El archivo Reporte_soho_junio_25 (1).xlsb usa formato binario .xlsb,
    que NO es compatible con openpyxl (solo .xlsx/.xlsm).

  DIAGNÓSTICO:
    .xlsb = Excel Binary Workbook (formato binario propietario)
    Para leerlo con Python se necesita la librería pyxlsb o pandas.

    Esto limita las opciones de automatización.

  SOLUCIÓN:
    Convertir el .xlsb a .xlsx usando Excel mismo (Guardar Como → .xlsx),
    o usar pandas para leerlo:

    ```python
    import pandas as pd
    df = pd.read_excel('reporte.xlsb', engine='pyxlsb')
    ```

    O instalar pyxlsb: pip install pyxlsb
